## 三、已修复的缺陷

### 3.1 F-1（高）CRLF 使 Linux 部署链失效 —— ✅ 已修复并复测通过

**问题**：仓库全树无 `.gitattributes` 且 `core.autocrlf=true`，461 个已跟踪文件工作区为 CRLF，含 `pnpm-lock.yaml` 与 4 个 `.sh`。`scripts/mysql-build-dependencies.mjs:16` 的 `lockServerVersions` 用**整行全等**匹配 `  server:`，CRLF 下行尾带 `\r` 永远匹配不到，直接抛「pnpm lock 缺少 server importer」。

**影响**：Linux 生产依赖构建不可用；若在 Windows 检出上打包，`prepare-baota-audit-release.mjs` 会把 CRLF 的 `update.sh` 发到 Linux，执行时报 `$'\r': command not found`。

**修复（三件套，缺一不可）**

| 步骤 | 动作 |
| --- | --- |
| 1 | 新增仓库根 `.gitattributes`：`* text=auto eol=lf`，脚本/配置显式 LF，二进制白名单 |
| 2 | 归一化工作区行尾：**461 个**文件 CRLF → LF |
| 3 | 重建索引：`git add --renormalize .` + `git reset` |

**复测证据**

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| `mysql-local-tools.test.mjs`（原失败 `:31`） | 3 通过 / 1 失败 | **4 通过 / 0 失败** |
| `mysql-baota-deployment.test.mjs`（原失败 `:76`） | 7 通过 / 1 失败 | **8 通过 / 0 失败** |
| 前端套件总体 | 165 通过 / 11 失败 | **167 通过 / 9 失败** |
| 工作区 CRLF 文件数 | 461 | **0** |

**过程中发现的坑（重要）**

- 只加 `.gitattributes` **不够**：属性只影响后续检出，不回溯改写工作区，461 个文件仍为 CRLF，用例照旧失败。
- 归一化工作区后 `git status` 出现 **461 条幻影 `M`**（`git diff` 对同一批文件报无差异）。根因是索引 stat 缓存失配；单独设 `core.autocrlf=false` **无效**，必须重建索引。最终 `git status` 由 474 条降至 **18 条**（5 真实改动 + 13 未跟踪）。
- 遗留待提交项：`source/server/src/regions/LICENSE-zoning.txt` 是索引中唯一的 `i/crlf`，归一后显示 42 行纯行尾差异，建议随下次提交纳入。

### 3.2 F-2（中）后台通用编辑接口可直写 `status` —— ✅ 已修复并复测通过

**问题**：`business/service.js:3558-3560` 的 submission 编辑分支把 `status` 放进可直接写入的顶层字段，使 `PATCH /api/v1/admin/business/<提交类资源>/:id` 能**绕过 `actAdmin` 的动作状态机**（`actionAllowed`），并**架空公益证书的唯一签发出口** `issue_certificate`（`:3753-3759` 的守卫原本只在 `/actions` 生效）。同一文件 `:3422-3442` 的受保护字段清单里**包含** `status`，说明这是遗漏而非设计。

**修复**：从 `topLevelKeys` 移除 `status`，改为显式抛 `BUSINESS_PROTECTED_FIELD`。

## 四、T09 专项复核（可推导初始口令 / 代理限流 / 越权 / 敏感字段 / 关闭模块绕过）

任务要求：「专项复核可推导初始口令、代理限流、越权、敏感字段和关闭模块绕过；提供复现及修复/有效隔离证据。」

本轮新增 `test/security-review.test.js`（**6 条，全部通过**），对上述 5 项逐一给出可执行复现与隔离证据。

| 专项 | 复核结论 | 证据 |
| --- | --- | --- |
| **可推导初始口令** | ⚠️ **发现缺陷（未修复）** | **口令哈希本身正确**：`hashPassword` 用 scrypt（N=16384/r=8/p=1）+ 每口令随机 16 字节盐，实测同一口令两次哈希不同；`verifyPassword` 用 `timingSafeEqual`、校验参数、拒绝损坏哈希；`randomToken` 用 `crypto.randomBytes(32)`；他人重置口令后旧会话立即撤销，未改密前调用管理接口返回 403 `PASSWORD_CHANGE_REQUIRED`。**但人员批量导入的初始口令是可推导的**——`personnel.js:89` 用 `hashPassword(row.username+'123456')`，且 `personnel.js:63` 的预检响应明文回显 `initialPasswordRule:'用户名后加123456，首次登录必须修改密码'`。攻击者知道/枚举到用户名即可抢在本人之前登录并借首位改密接管账号。详见 HUFE-001 |
| **代理限流** | ✅ 无缺陷，且有防误配 | `trustProxy` **默认 false**（`config.js:114`），默认忽略 `X-Forwarded-For`。实测**轮换 XFF 二十次仍被按 IP 限流拦下**（第 16 次起 429 `RATE_LIMITED`）。`trustedProxyPolicy` **拒绝信任全部来源**：未配置 CIDR 时直接抛「不能信任所有来源」，`0.0.0.0/0` 与 `::/0` 被拒（`prefix < 1` 校验），非法条目被拒 |
| **越权** | ✅ 无缺陷 | 90 条 admin 路由**无一条缺守卫**（见 §五 安全阻断项复核）；非管理员访问后台接口 **401**，伪造 token **401**；委派管理员受记录级隔离与事务内复检约束（`delegation-flow.test.js` 6 条） |
| **敏感字段** | ✅ 无缺陷 | 实测账号列表与 `/api/v1/me` 响应**不含** `passwordHash`/`schoolSubjectKey`/`studentIdKey`/`idCardKey` 等身份键；匿名动态视图**不含** `authorAccountId`/`adminNote`。数据库仅存身份证**掩码 + HMAC**，原始值被显式 `delete`（`auth/identity.js:177-182`） |
| **关闭模块绕过** | ✅ 有效隔离 | 关闭 `community` 后，逐一尝试 7 种 URL 变体（尾斜杠、带 query、双斜杠、`./`、百分号编码、admin 前缀）**均无法返回 200**；发布接口同样被拦；重新开启后**恢复正常且数据未损** |

**结论**：5 个专项方向中 **4 项未发现可利用缺陷**（代理限流、越权、敏感字段、关闭模块绕过），**1 项发现真实缺陷**——「可推导初始口令」在人员批量导入路径上成立（新表 HUFE-002，**未修复**）。该缺陷由 `docs/testing/项目技术测试记录表.md` 记录，并已据此修正本节原先「无缺陷」的判定。
